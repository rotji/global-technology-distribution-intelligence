# API and MCP Opportunities

**Research status:** Exploratory; no product build approved  
**As-of date:** 21 November 2026

## Purpose
Investigate whether specialist data, intelligence, verification, monitoring or workflows could be made available to websites, applications, enterprise systems and AI agents through APIs, MCP or other permitted integrations.

## Core distinctions
- **API:** a programmatic interface through which software requests data or performs an operation.
- **MCP:** a protocol for exposing tools and context to compatible AI applications and agents.
- **Website:** a human-facing interface for discovery, configuration, reporting, accounts and support.
- **Agent:** a software actor that may invoke a tool, but does not automatically own the budget, credentials, contract or payment authority.

These mechanisms can complement one another. They do not independently create customers, demand, payment or legal permission to access data.

## Capability categories to investigate
- Verified and structured datasets.
- Data discovery and matching.
- Entity, supplier or claim verification.
- Change detection and monitoring.
- Market, price and operational intelligence.
- Geospatial and location intelligence.
- Risk and compliance signals.
- Specialist research and decision-support workflows.

These are capability categories, not approved products or established market opportunities. Each requires a specific user, decision, buyer, data source, evidence standard and value proposition.

## Commercial questions
1. Which person or organisation experiences a recurring, costly or important problem?
2. Who would procure and pay for the capability?
3. What decision or workflow would it improve?
4. What information or action is difficult to obtain through existing platforms?
5. Which providers already offer the capability?
6. Can existing APIs, MCP servers, connectors or services be assembled instead of building?
7. What data rights, source permissions and redistribution terms apply?
8. How would authentication, authorisation, metering, rate limits, reliability and support work?
9. What would the customer pay for: access, usage, subscription, report, verified result or outcome?
10. What are the hosting, data acquisition, maintenance, security and support costs?

## Access and payment architecture
An application or enterprise operator may hold the account, credentials and budget authorising use of an API or MCP tool. An AI agent can act within delegated permissions, but protocol compatibility alone does not guarantee the agent can purchase access or that the provider will be paid.

Any commercial design must identify the contracting customer, authorised account holder, billing relationship, usage measurement, permitted agent actions and support process.

## Existing capability before building
Before designing a proprietary API or MCP service, compare existing data providers, APIs, MCP servers, platforms, connectors and service operators. Consider partnership, integration, implementation or distribution. Do not build a generic agent or data platform merely because it is technically possible.

## Current decision
Continue market and capability research only. No API, MCP server, website product or agent platform is approved for development. A build proposal requires evidence of a material gap, a concrete buyer or customer request, lawful access to differentiated data, feasible operations and explicit user approval.
